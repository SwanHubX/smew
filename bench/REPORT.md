# smew JS(TS) vs WASM 性能基准

- 日期：2026-10-22T03:34:43.457Z
- 运行环境：Node v24.16.0 / darwin arm64 / Apple M5 × 10 核
- 档位：full（每格 1 亿点：S1 = 100,000 次调用 × 1,000 点，S2 = 1,000 次调用 × 100,000 点），轮数：3
- 口径：e2e = 业务对象 → 结果（Float64Array 边界转换计入 WASM 侧）；pure
  = 各自原生输入，只计时平滑本体（术语详见下方「术语说明」）
- 注意：这是 Node 侧数字，不能外推为浏览器性能；建议接电源 / 高性能模式运行

## 术语说明

| 术语             | 含义                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 格               | 一组固定条件的测试。本次矩阵 = 2 场景 × 2 数据形态 × 4 算法参数 × 3 测法 = 48 格，每格独立计时                            |
| 点               | 曲线上的单个数据值（某一步记录的指标值）；一条曲线 = 一个点的序列                                                         |
| 一次调用（批次） | 对一条曲线完整跑一次平滑。S1 = 10 万条短曲线（每条 1 千点）；S2 = 1 千条长曲线（每条 10 万点）；两场景总量同为每格 1 亿点 |
| 档位             | 测试规模。quick = 每格 1000 万点（约 2 分钟，验证脚本用）；full = 每格 1 亿点（约 10 分钟，正式数字）                     |
| 轮数             | 每格完整重复的遍数（本次 3 轮），降低单次测量撞上系统抖动 / GC 的运气成分                                                 |
| 中位数           | 排序后居中的值。吞吐取 3 轮中位数，不被最好或最差的一轮带偏                                                               |
| p50 / p95 / p99  | 单调用耗时：p50 = 一半调用比它快（典型情况）；p95 = 仅 5% 慢于此；p99 = 仅 1% 慢于此（最慢尾巴，多由 GC 卡顿造成）        |
| 吞吐             | 每秒处理多少"百万个点"（M/s），越大越快                                                                                   |
| 口径             | 秒表从哪里开始掐，见下                                                                                                    |

**两种口径**（秒表按的位置不同，回答的问题不同）：

- **pure（纯计算）**：各喂各的原生格式（TS 吃对象数组、WASM 吃 Float64Array），秒表只掐算法本身。回答"Rust 算法本身比 JS 快多少"
- **e2e（端到端）**：两边都从同一份业务对象数组出发到最终结果。WASM 只认 Float64Array，所以多一步"对象拆包 → 计算 → 装包回对象"，全程计时。回答"App 实际使用能快多少"
- 两口径的差值即 WASM 边界转换成本（本报告核心发现之一：S1 场景 TWE 的 e2e 耗时约 74% 来自拆装包）

## 一句话结论

同一批数据，JS 版和 WASM 版各跑一遍比速度，同时核对两边算出的数是否一致。结果：
**数据越大 WASM 越快（纯算法最快 11-12 倍），数据切得碎时拆装包吃掉收益（最差只剩 1.28 倍），但 WASM 永远不吃亏；两边数值一致（ck 抽样核对，完整一致性由 parity 测试保证）。**

## 结论（TL;DR）

随机序列（真实形态）下的加速比 **WASM/JS** 汇总：

| 场景            | 口径 | TWE@0.5    | TWE@0.98   | RA@10     | GS@3  |
| --------------- | ---- | ---------- | ---------- | --------- | ----- |
| S2 少批次大数据 | e2e  | 1.93×      | 2.07×      | 1.93×     | 2.33× |
| S2 少批次大数据 | pure | **11.42×** | **11.78×** | 2.59×     | 2.80× |
| S1 多批次小数据 | e2e  | 1.59×      | 1.65×      | **1.28×** | 1.73× |
| S1 多批次小数据 | pure | 5.75×      | 5.92×      | 1.51×     | 1.89× |

1. **大数据（S2）WASM 明显快**：纯计算口径 TWE 快 11-12 倍，RA/GS 快 2.3-2.8 倍；即便计入边界转换，e2e 也有 1.9-2.3 倍。TS 侧单次 10 万点调用 p50 约 1.7-19ms，WASM 纯算仅 0.24-6.7ms。
2. **小数据多批次（S1）差距收窄但不反转**：e2e 最小收窄到 1.28×（RA@10）。WASM 仍始终领先，"边界开销吃掉收益"的方向被证实，但本机未出现反超。
3. **边界转换是 WASM 路径的主要成本**：S1 中 TWE WASM 单调用 p50 为 9.8µs，其中纯计算仅 2.6µs——约 **74% 耗在 toValues +
   withSmoothedData**（对象拆包/装包）。若未来要放大小批量场景收益，优化方向是削减这两处的对象分配，而不是算法本体。
4. **算法间差异显著**：TWE 获益最大（TS 每点新建/展开对象 vs
   WASM 纯 f64 循环）；RA/GS 的 TS 实现本就是数值密集循环，加速比仅 1.3-2.9×。
5. **常数序列（safeLerp a===b 快速分支）未出现 TS 反超**：TS 提速 5%-43%（S2 RA 最明显），但 WASM 同样受益（TWE
   pure 从约 390M/s 升至约 530M/s），两侧差距反而拉大到 12.5-12.7×。e2e 口径下常数与随机几乎无差别（转换主导）。
6. **工程结论**："WASM 优先 +
   TS 回退"的调度在两种负载形态下均不吃亏（最差仍有 1.28× 收益）；小批量场景单调用 p50 两侧均在 10-130µs 量级、远低于一帧（16ms），用户层面无感知差异，WASM 的价值主要在大序列。

## 一个关键发现：延迟的“长尾”

注意“最慢”那一列——JS 版的最差调用常是典型值的 2-6 倍（如 S2 随机 TWE@0.5：典型 1.736ms
→ 最慢 10.263ms，5.9 倍），这是垃圾回收卡顿；WASM 版长尾短得多（3.467ms）。**WASM 不只是更快，卡顿也更少**——对“拖动滑块要跟手”的交互场景，这点比平均速度更值钱。

## 数值一致性（checksum）

checksum（ck）= 每次调用后从输出头/中/尾抽样累加出的指纹。它证明两件事：

**① 结果被真实消费了**（防止 JIT 把“没人用的计算”整个优化掉）

**②JS 和 Rust/WASM 两套实现的输出相互印证**（同格三路喂同一批种子固定数据，ck 完全相同。注意 ck 只抽样头/中/尾三点，相同是必要证据而非全序列等价证明——完整逐位一致性由 tests/parity.test.ts 保证）

## 复现方式

```bash
# 在 smew 目录（或仓库根目录 npm run bench -w smew -- ...）
npm run bench -- --scale full --out bench/results-full.md   # 正式数字（每格 1 亿点，约 10 分钟）
npm run bench -- --scale quick                              # 快速档（每格 1000 万点，约 2 分钟）
npm run bench -- --scale quick --only s2/random/TWE@0.5     # 只跑匹配的格子（调试用）
```

可复现性：数据由 LCG 种子固定生成（seed
42..49，与 tests/parity.test.ts 同款发生器）；同配置两次运行的 checksum 应逐位一致（见上）。

## 方法说明（怎么测的）

- 每格：先 warmup（不计时）→ 3 轮正式；吞吐 = 总点数 ÷ 轮时长中位数，延迟分位数跨轮合并
- 单调用以 performance.now 夹住计时；TS 侧含 await 完成（async 开销如实计入，App 亦如此调用）
- 结果消费在计时窗口外（checksum 抽样累加，防死代码消除）；输入池 8 条序列轮转
- WASM e2e 的边界转换逐行复刻 smew/index.ts 的 toValues / withSmoothedData，计入 WASM 侧
- 亚毫秒级单调用延迟受计时器粒度影响（S1 小批量 WASM 调用为微秒级，分位数仅供参考）
