# PR 与分支

**适用范围**：所有分支与 Pull Request **读完能回答**：分支怎么命名、PR 标题与描述写什么、怎么锚定 issue

## 必须遵守

### 1. 语言

- 分支名与 PR 标题用英文。
- PR 描述与评论正文用中文。

### 2. 分支名

- 用英文表达改动主题，不写中文。
- 一个分支只对应一个目标；混入无关改动会破坏 PR 的范围判断。
- 直推分支用 `feat/` 前缀；`feature/**` 保留给必须走 PR 的正式分支。

### 3. PR 标题

- 用英文说明这次合并带来了什么。
- 不用无信息量的标题，例如 `update` / `fix`。

### 4. PR 描述

PR 描述模板见
[`.github/pull_request_template.md`](../../.github/pull_request_template.md)。字段与顺序以模板为准，本文不重复维护；各节要求：

- `## 总结`：2~4 行说明这次合并带来什么，必要时附结构树；面向人类评审。
- `## 需求`：写 `Closes #123`；中间交付用 `Refs` 并说明覆盖了哪些验收项，最后一个 PR 用 `Closes`。
- `## 方案来源`：定稿评论 permalink 与 3~5 行摘要。摘要不是重复：评论可编辑，PR 描述是合并时冻结的快照。
- `## 改动`：按模块列出实际改动，3~6 条；不复述 diff。
- `## 验收`：逐条对应 issue 验收标准，每条附证据，即命令与结果或手工验证的场景；未覆盖项写明原因。
- `## 风险`：未覆盖场景、已知限制。

一个 PR 覆盖多个 issue 时，说明各自对应关系。

### 5. 锚定 issue

- 需求与方案以 issue 正文和定稿评论为准：issue 正文放背景与验收标准，方案以定稿评论沉淀。
- 纯文档、格式调整、依赖升级、紧急修复可以不开 issue，但 PR 描述必须写明豁免原因与影响范围。

### 6. 合并需人工确认

- 未获仓库所有者明确确认，禁止执行任何 merge（含 `gh pr merge` 与本地合并到 main）。
- agent 只负责开 PR、跟进 CI、回复 review；合并动作等用户指令。
- CI 绿不等于可以合并；CI 通过只是合并的前提条件之一。

## 常见错误

| 错误                   | 正解                               |
| ---------------------- | ---------------------------------- |
| 分支名或 PR 标题用中文 | 改成英文                           |
| PR 描述只写"改了什么"  | 补需求、方案来源、验收与风险       |
| 验收没有逐条对应 issue | 按验收标准逐条标注通过或未覆盖原因 |
| 用 `Refs` 当作关闭     | 最后一个 PR 用 `Closes`            |
| 多个 issue 混在一个 PR | 说明对应关系，或拆分为独立 PR      |
| 豁免场景不写原因       | 在描述中写明豁免依据与影响范围     |
| agent 自行 merge       | 等仓库所有者明确确认               |

## 判断边界

- PR 描述不重复 diff；代码细节交给 review。
- 分支名与 PR 标题只要求英文与可读，不强制固定格式。
- 合并后 PR 描述不再改写；方案变化在 issue 评论中留痕。
